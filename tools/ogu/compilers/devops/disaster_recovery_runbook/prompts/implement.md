# Disaster Recovery Runbook — Implementation Guide

## Purpose

An untested DR runbook is a document, not a runbook — the only way to know it still works
is to run it regularly, because systems change and procedures decay. A scenario without an
owner means that during an actual disaster, no one is accountable for executing those steps.
`rpo > rto` means you are committed to losing more data than the time it takes to recover —
an operationally inconsistent SLA that will cause confusion during incident postmortems.
Duplicate scenario names mean on-call engineers cannot determine which procedure to follow
under pressure. A runbook with no data-loss scenario means the highest-cost incident class
is entirely unplanned. This compiler enforces all of these constraints before emitting an artifact.

## Invariants

| Code  | Gate                        | What It Enforces |
|-------|-----------------------------|------------------|
| DR001 | spec-valid                  | `dr-runbook-spec.json` exists, is valid JSON; `service`, `rto`, `rpo`, and `scenarios` (non-empty) are declared |
| DR002 | rto-rpo-defined             | `rto` and `rpo` are valid ISO 8601 durations; `rpo` ≤ `rto`; `rto` > 24h requires `skipRTOWarning: true` |
| DR003 | scenarios-complete          | Every scenario has `name`, `trigger`, `steps` (non-empty), and `owner`; every step has `action` |
| DR004 | failover-targets-valid      | When `failover` is declared: `primaryRegion` ≠ `secondaryRegion`, valid `strategy` (skipped if no failover) |
| DR005 | communication-plan-defined  | `incidentCommander`, `escalationPath` (non-empty), and `statusPageUrl`/`statusChannel` required (skipped with `skipCommunicationPlan: true`) |
| DR006 | test-schedule-defined       | `testSchedule.frequency` or `testSchedule.cron` must be declared (skipped with `skipTestSchedule: true`) |
| DR007 | no-todos                    | `dr-runbook-spec.json` contains no `TODO`, `FIXME`, `HACK`, `XXX`, or `PLACEHOLDER` |
| DR008 | contract-dr-runbook         | Unique scenario names; at least one data-loss scenario; every scenario has `owner`; `service` matches workload artifact when present |

## Required Output Files

- `dr-runbook-spec.json` — author-maintained DR runbook declaration
- `dr-runbook-artifact.json` — generated by the compiler on full gate pass

## dr-runbook-spec.json Structure

```json
{
  "service": "payments-api",
  "rto": "PT4H",
  "rpo": "PT30M",
  "scenarios": [
    {
      "name": "database-restore",
      "trigger": "Accidental table drop or data corruption detected in production",
      "owner": "data-platform-oncall",
      "steps": [
        { "action": "Page data-platform-oncall via PagerDuty" },
        { "action": "Identify most recent clean snapshot in S3" },
        { "action": "Restore snapshot to dr-sandbox environment and verify row counts" },
        { "action": "Promote restored database to production after approval" }
      ]
    },
    {
      "name": "region-failover",
      "trigger": "AWS us-east-1 becomes unavailable for more than 15 minutes",
      "owner": "sre-oncall",
      "steps": [
        { "action": "Confirm regional outage via AWS Health Dashboard" },
        { "action": "Trigger Route 53 failover to eu-west-1" },
        { "action": "Verify service health in eu-west-1 via health check endpoint" }
      ]
    }
  ],
  "failover": {
    "primaryRegion": "us-east-1",
    "secondaryRegion": "eu-west-1",
    "strategy": "active-passive"
  },
  "communicationPlan": {
    "incidentCommander": "sre-on-call",
    "escalationPath": ["sre-manager", "vp-engineering", "cto"],
    "statusPageUrl": "https://status.example.com",
    "statusChannel": "#incidents"
  },
  "testSchedule": {
    "frequency": "quarterly"
  }
}
```

## Field Reference

| Field                                    | Required    | Notes |
|------------------------------------------|-------------|-------|
| `service`                                | yes (DR001) | Service name — must match Kubernetes workload when artifact is present |
| `rto`                                    | yes (DR001) | Recovery Time Objective — ISO 8601 duration |
| `rpo`                                    | yes (DR001) | Recovery Point Objective — must be ≤ rto |
| `scenarios`                              | yes (DR001) | Non-empty array of DR scenarios |
| `scenarios[].name`                       | yes (DR003) | Unique scenario identifier |
| `scenarios[].trigger`                    | yes (DR003) | Condition that activates this scenario |
| `scenarios[].owner`                      | yes (DR003) | On-call role or team responsible for execution |
| `scenarios[].steps`                      | yes (DR003) | Non-empty array of step objects |
| `scenarios[].steps[].action`             | yes (DR003) | Executable step description |
| `failover.primaryRegion`                 | yes (DR004) | Primary cloud region (when failover declared) |
| `failover.secondaryRegion`               | yes (DR004) | Failover region — must differ from primary |
| `failover.strategy`                      | yes (DR004) | See failover strategy reference |
| `communicationPlan.incidentCommander`    | yes (DR005) | Named commander for the incident |
| `communicationPlan.escalationPath`       | yes (DR005) | Non-empty array of escalation contacts |
| `communicationPlan.statusPageUrl`        | conditional | Public status page (DR005 requires this or `statusChannel`) |
| `communicationPlan.statusChannel`        | conditional | Internal status channel (e.g. `#incidents`) |
| `testSchedule.frequency`                 | conditional | Named frequency (DR006 requires this or `cron`) |
| `testSchedule.cron`                      | conditional | 5-field cron expression |
| `skipRTOWarning`                         | no          | `true` to acknowledge rto > 24h |
| `skipCommunicationPlan`                  | no          | `true` to exempt from DR005 |
| `skipTestSchedule`                       | no          | `true` to exempt from DR006 |
| `skipDataLossScenario`                   | no          | `true` to exempt from DR008 data-loss requirement |
| `skipWorkloadMatch`                      | no          | `true` to exempt from DR008 workload name check |

## ISO 8601 Duration Format (DR002)

| String   | Meaning |
|----------|---------|
| `PT30M`  | 30 minutes |
| `PT1H`   | 1 hour |
| `PT4H`   | 4 hours |
| `PT12H`  | 12 hours |
| `P1D`    | 1 day |

**Do not use**: `"4 hours"`, `"30 minutes"`, `"1 day"` — these are plain English, not ISO 8601.

## Failover Strategy Reference (DR004)

| Strategy         | Description |
|------------------|-------------|
| `active-active`  | Traffic flows to both regions simultaneously — instant failover |
| `active-passive` | Secondary region receives traffic only on failover — requires DNS or load balancer switch |
| `pilot-light`    | Secondary has minimal resources running; scales up on failover |
| `warm-standby`   | Secondary is fully configured but not serving production traffic |

## Test Schedule Frequency Reference (DR006)

| Frequency    | Recommended For |
|--------------|-----------------|
| `daily`      | Automated smoke tests only |
| `weekly`     | Active-active systems with frequent change |
| `monthly`    | Standard production services |
| `quarterly`  | Most services — minimum recommended |
| `annually`   | Low-change, high-stability services |

## Error Codes

| Code  | Trigger | Fix |
|-------|---------|-----|
| DR001 | `dr-runbook-spec.json` missing | Create with `service`, `rto`, `rpo`, and `scenarios: [...]` |
| DR001 | `scenarios: []` | Add at least one scenario |
| DR001 | Missing `rto` or `rpo` | Add `"rto": "PT4H"` and `"rpo": "PT30M"` |
| DR002 | `rto: "4 hours"` | Use ISO 8601: `"PT4H"` |
| DR002 | `rpo: "PT6H"` > `rto: "PT4H"` | rpo must be ≤ rto — set rpo to `"PT30M"` or extend rto |
| DR002 | `rto: "P3D"` (exceeds 24h) | Add `"skipRTOWarning": true` if approved, or reduce rto |
| DR003 | Scenario missing `trigger` | Add `"trigger": "condition that activates this scenario"` |
| DR003 | Scenario missing `owner` | Add `"owner": "sre-oncall"` |
| DR003 | Scenario `steps: []` | Add at least one step with `"action": "..."` |
| DR003 | Step missing `action` | Add `"action": "what to do"` to the step |
| DR004 | `primaryRegion === secondaryRegion` | Choose regions in separate geographic locations |
| DR004 | `strategy: "standby"` | Use `"warm-standby"` — `"standby"` is not recognised |
| DR004 | Missing `primaryRegion` | Add `"primaryRegion": "us-east-1"` |
| DR005 | No `communicationPlan` | Add a `communicationPlan` block with `incidentCommander` and `escalationPath` |
| DR005 | No `incidentCommander` | Add `"incidentCommander": "sre-oncall"` |
| DR005 | No `escalationPath` | Add `"escalationPath": ["sre-manager", "vp-eng"]` |
| DR005 | No `statusPageUrl` and no `statusChannel` | Add `"statusChannel": "#incidents"` |
| DR006 | No `testSchedule` | Add `"testSchedule": { "frequency": "quarterly" }` |
| DR006 | `frequency: "yearly"` | Use `"annually"` |
| DR007 | `"action": "TODO: fill in"` | Write a real step action |
| DR008 | Duplicate scenario names | Rename — each scenario name must be unique |
| DR008 | No data-loss scenario | Add scenario with `"name"` matching `/backup|restore|data-loss|recover/` |
| DR008 | `service: "payments"` ≠ workload `"payments-api"` | Align `spec.service` with the Kubernetes workload name |
