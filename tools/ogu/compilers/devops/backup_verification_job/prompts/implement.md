# Backup Verification Job — Implementation Guide

## Purpose

A backup that has never been restored is not a backup — it is an untested assumption. This compiler
enforces that backup verification is automated, targets a non-production environment, validates
actual data integrity with queries, writes a retrievable result artifact, and alerts on failure.
A verification that restores to production risks corrupting live data. A verification without
queries can only confirm the restore process completed — it cannot confirm the data is correct.
A verification with no failure alerting silently fails and the organization believes backups are
healthy until a real incident proves otherwise.

## Invariants

| Code  | Gate                   | What It Enforces |
|-------|------------------------|------------------|
| BV001 | spec-valid             | `backup-verify-spec.json` exists, is valid JSON; `backupSource`, `restoreTarget`, and `verifyQueries` are declared |
| BV002 | target-non-production  | `restoreTarget` must not be production/prod/live/prd without `productionOverride: true` |
| BV003 | verify-queries-defined | `verifyQueries` must be a non-empty array — a restore with no validation provides no confidence |
| BV004 | result-artifact-path   | `resultArtifactPath` must be declared so verification outcomes are retrievable after job completion |
| BV005 | schedule-or-trigger    | `schedule` (cron) or `trigger` (event) must be declared — manual-only verification is unreliable |
| BV006 | no-todos               | `backup-verify-spec.json` contains no `TODO`, `FIXME`, `HACK`, `XXX`, or `PLACEHOLDER` markers |
| BV007 | contract-backup-verify | `owner` must be declared; `notifyOnFailure: true` or `alertChannel` must be set |

## Required Output Files

- `backup-verify-spec.json` — author-maintained verification job declaration
- `backup-verify-artifact.json` — generated by the compiler on full gate pass

## backup-verify-spec.json Structure

```json
{
  "backupSource": "s3://my-backups/postgres/latest.dump",
  "restoreTarget": "dr-sandbox",
  "owner": "data-team",
  "schedule": "0 5 * * 1",
  "alertChannel": "pagerduty",
  "resultArtifactPath": ".ogu/backup-verify-results.json",
  "verifyQueries": [
    {
      "sql": "SELECT COUNT(*) FROM users WHERE created_at > NOW() - INTERVAL '7 days'",
      "expectedMin": 1,
      "description": "At least one user created in the last 7 days"
    },
    {
      "sql": "SELECT 1 FROM schema_migrations ORDER BY version DESC LIMIT 1",
      "expectedMin": 1,
      "description": "Schema migrations table is populated"
    }
  ]
}
```

## Field Reference

| Field               | Required    | Notes |
|---------------------|-------------|-------|
| `backupSource`      | yes (BV001) | Path or URL to the backup to restore |
| `restoreTarget`     | yes (BV001) | Environment name — must not be production |
| `verifyQueries`     | yes (BV001) | Non-empty array of integrity queries |
| `resultArtifactPath`| yes (BV004) | Where to write the verification result |
| `owner`             | yes (BV007) | Team or email for on-call routing |
| `schedule`          | conditional | Cron expression (BV005 requires this or `trigger`) |
| `trigger`           | conditional | Event-based trigger (BV005 requires this or `schedule`) |
| `notifyOnFailure`   | conditional | `true` to enable failure notifications (BV007 requires this or `alertChannel`) |
| `alertChannel`      | conditional | Channel name for failure alerts |
| `productionOverride`| no          | `true` to allow production restore targets |

## Verify Query Structure

```json
{
  "sql": "SELECT COUNT(*) FROM orders WHERE status = 'completed'",
  "expectedMin": 100,
  "description": "At least 100 completed orders (data loss indicator if fewer)"
}
```

| Field         | Notes |
|---------------|-------|
| `sql`         | SQL query to run against the restored database |
| `expectedMin` | Minimum rows/count expected — fails if result is below this |
| `description` | Human-readable explanation of what this query validates |

## Error Codes

| Code  | Trigger | Fix |
|-------|---------|-----|
| BV001 | `backup-verify-spec.json` missing | Create the file with `backupSource`, `restoreTarget`, `verifyQueries` |
| BV002 | `restoreTarget: "production"` | Change to `"dr-sandbox"` or `"staging"` — or add `productionOverride: true` with justification |
| BV003 | `verifyQueries: []` | Add at least one SQL query that validates real data presence |
| BV003 | No `verifyQueries` | Add `verifyQueries: [{ sql: "SELECT COUNT(*) FROM users", expectedMin: 1 }]` |
| BV004 | No `resultArtifactPath` | Add `resultArtifactPath: ".ogu/backup-verify-results.json"` |
| BV005 | No `schedule` and no `trigger` | Add `schedule: "0 5 * * 1"` (Monday at 5am) or an event trigger |
| BV007 | No `owner` | Add `owner: "data-team"` |
| BV007 | No `notifyOnFailure` and no `alertChannel` | Add `alertChannel: "pagerduty"` or `notifyOnFailure: true` |
