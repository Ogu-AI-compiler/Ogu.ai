# Vault Policy Compiler — Implementation Guide

## Purpose

Define a HashiCorp Vault policy that grants least-privilege access. A policy with a wildcard
path (`secret/*`) grants access to every secret created under that prefix now and in the
future — including secrets not yet imagined. A policy missing `owner` becomes an orphaned
access grant that survives team changes and is never cleaned up. A Kubernetes role without
`namespace` lets any namespace's service account authenticate against Vault. This compiler
enforces correctness and accountability before emitting an artifact.

## Invariants

| Code  | Gate                    | What It Enforces |
|-------|-------------------------|------------------|
| VP001 | spec-valid              | `vault-policy-spec.json` exists, is valid JSON; `name`, `paths` (non-empty), and `roles` are required; every path entry has a `path` string and non-empty `capabilities` |
| VP002 | roles-declared          | Every role referenced in path entries is declared in the top-level `roles` array — undeclared roles cause auth failures at runtime |
| VP003 | no-wildcard-paths       | Paths with `*` or `+` wildcards must include `wildcardException: "reason"` — wildcards grant access to all current and future secrets under the prefix |
| VP004 | capabilities-allowed    | All capabilities must be from the allowed set: `create`, `read`, `update`, `delete`, `list`, `patch`, `sudo`, `deny`. Typos are silently ignored by Vault |
| VP005 | least-privilege         | Paths under `sys/raw`, `sys/mount`, or `auth/token/root` are blocked unless `allowRootAccess: true` is set with justification |
| VP006 | paths-in-allowed-prefix | When `allowedPrefixes` is declared, every path must start with one of those prefixes (skipped when `allowedPrefixes` is absent) |
| VP007 | no-todos                | `vault-policy-spec.json` contains no `TODO`, `FIXME`, `HACK`, `XXX`, or `PLACEHOLDER` markers |
| VP008 | contract-vault-policy   | `description` and `owner` are required; Kubernetes SA roles must specify `namespace` to scope the auth binding |

## Required Output Files

- `vault-policy-spec.json` — policy declaration (name, paths, capabilities, roles)
- `vault-policy-artifact.json` — generated by the compiler on full gate pass

## vault-policy-spec.json Structure

```json
{
  "name": "orders-service-policy",
  "description": "Grants read access to database credentials and shared config for the orders service",
  "owner": "platform-team",
  "allowedPrefixes": ["secret/data/orders/", "secret/data/shared/"],
  "paths": [
    {
      "path": "secret/data/orders/db-credentials",
      "capabilities": ["read"]
    },
    {
      "path": "secret/data/shared/config",
      "capabilities": ["read", "list"]
    },
    {
      "path": "secret/data/orders/*",
      "capabilities": ["read", "list"],
      "wildcardException": "team-scoped read-only access — only the orders service namespace can authenticate"
    }
  ],
  "roles": [
    {
      "name": "orders-k8s-role",
      "serviceAccount": "orders-service",
      "namespace": "production"
    }
  ]
}
```

| Field             | Required     | Notes |
|-------------------|--------------|-------|
| `name`            | yes          | Used in IR ID: `VAULT_POLICY:{name}` |
| `description`     | yes (VP008)  | Explains what access this policy grants and why |
| `owner`           | yes (VP008)  | Team responsible for this access grant |
| `paths`           | yes          | Non-empty array; each entry needs `path` + `capabilities` |
| `roles`           | yes          | Array (can be empty if no auth bindings yet) |
| `allowedPrefixes` | no           | When set, all paths must start with one of these prefixes |
| `wildcardException` | conditional | Required when a path contains `*` or `+` |
| `allowRootAccess` | conditional  | Required when a path is under `sys/raw` or `sys/mount` |

## Vault Capabilities Reference

| Capability | What It Grants |
|------------|----------------|
| `read`     | Read secret values |
| `list`     | List secret keys (not values) |
| `create`   | Create new secrets |
| `update`   | Overwrite existing secrets |
| `delete`   | Delete secrets |
| `patch`    | Partially update a secret |
| `sudo`     | Override root-protected paths (rarely needed) |
| `deny`     | Explicit deny (overrides any allow) |

## Error Codes

| Code  | Trigger | Fix |
|-------|---------|-----|
| VP001 | `vault-policy-spec.json` missing | Create the file with `name`, `paths`, and `roles` |
| VP001 | Path entry with no `capabilities` | Add `capabilities: ["read"]` to the path entry |
| VP002 | Role referenced in a path but not in `roles` | Add the role to the top-level `roles` array |
| VP003 | `path: "secret/data/orders/*"` with no `wildcardException` | Add `wildcardException: "team-scoped read-only"` to the path entry |
| VP004 | `capabilities: ["superuser"]` | `superuser` is not a Vault capability — use `sudo` or `read`/`write` |
| VP005 | `path: "sys/raw/config"` without `allowRootAccess` | Add `allowRootAccess: true` with justification, or remove the path |
| VP006 | Path not matching any `allowedPrefixes` | Either add the prefix to `allowedPrefixes` or narrow the path |
| VP008 | No `description` | Add `description: "Grants read access to X for the Y service"` |
| VP008 | No `owner` | Add `owner: "platform-team"` |
| VP008 | Role with `serviceAccount` but no `namespace` | Add `namespace: "production"` to scope the Kubernetes auth binding |
